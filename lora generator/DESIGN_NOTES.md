# LoRA Training — Design Notes

> Written 2026-09-22 after the first successful `midway-coder-lora` training run.

## Architecture: modular datasets → one combined adapter

Training data is generated by modular, concern-scoped generators and fused into
a single JSONL before training:

| Concern | Generator | What it teaches |
|---|---|---|
| Edit protocol | `search_replace_lora_generator.py` | SEARCH/REPLACE discipline |
| Domain contract | `cartridge_lora_generator.py` | Cartridge API facts |
| Paging protocol | `lora_dataset_generator.py` | Context-management signals |

`combine_datasets.py` merges them into `combined_lora_dataset.jsonl`, which is
fed to `lora_fine_tune.py` to produce **one** adapter.

**Hard constraint:** Ollama loads exactly ONE `ADAPTER` per model. Runtime
composition of multiple LoRAs is not possible, so modularity lives at the
dataset + training level, not at the deployment level. The deployment artifact
is a single adapter (or a single merged GGUF).

## Design decision: the Wizard generates per-cartridge contract data

**Problem.** A cartridge's contract — its API surface, naming conventions, and
semantics — varies wildly from project to project. `MidwayPhysics.*` has
nothing in common with a future "Space Pinball" or "Fishing Derby" cartridge.
Today's `cartridge_lora_generator.py` is Midway-flavored (its SPAWN / POOL /
ECONOMY scenarios are hardcoded to the Midway contract), so it will NOT
transfer to a new project.

**Decision.** The **Acquisition Wizard** (`acquisition_wizard.py`) is
responsible for generating the contract training data for each cartridge it
builds. Contract data is per-project and must be produced at cartridge-build
time, not maintained as a static shared dataset.

**Hooks:**
- `acquisition_wizard.py` phase 5 ("Integrating into cartridge") is the natural
  place to emit LoRA training samples. The wizard already collects and
  integrates the knowledge; it should additionally write ChatML JSONL samples.
- Cartridge classes already expose structured contract metadata via
  `get_bridge_contract()` / `get_review_prompt_extra()`. The wizard should turn
  that metadata into training samples in the SAME ChatML format as the other
  datasets (so `combine_datasets.py` can ingest them unchanged).
- Generalize `cartridge_lora_generator.py`: accept a cartridge class / contract
  metadata as input instead of hardcoding Midway scenario content. Keep the
  scenario *shapes* (spawn, fix-phantom, lifecycle, etc.) but fill them from
  the wizard-supplied contract.

**Loss policy.** Contract data is factual (the model must memorize which
functions exist and their signatures), so it trains with `train_on_inputs=true`
(full-sequence loss). See `DATASET_TRAIN_ON_INPUTS` in `lora_config.py`
(keyed by `"cartridge"` / `"midway"`).

## Explicitly rejected: per-language LoRAs

A LoRA should teach what the base model (Qwen2.5-Coder) does NOT already know.
The base model already knows C++, Lua, and JoltPhysics from pretraining, so a
"C++ LoRA" / "Lua LoRA" / "Jolt LoRA" would mostly retrain existing knowledge
for little gain. When the coder emits bad code it is almost always a contract
or protocol failure, not a language failure. The valuable LoRA axes are
**protocol / contract / paging**, not language.
